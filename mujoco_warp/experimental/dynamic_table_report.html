Experimental engineering report / DynamicTable

Stable columns.
Dynamic rows.

DynamicTable is a GPU component store: it appends and deletes entities, packs surviving rows by world, and keeps the addresses of its columns stable. Logical populations can change inside a CUDA graph. Physical memory growth has an explicit host boundary.

1. A table shared by many worlds

Each component is a contiguous array. Every live row has a world ID and an entity identity. Worlds share one logical capacity rather than receiving equal slices.

For a particle table, columns might be position, velocity, and age. A contact table uses position, normal, signed depth, and geometry IDs. All columns have the same reserved row shape, even when only a prefix is physically backed and only a smaller prefix contains live rows.

Three different counts

max_rows is the address-space reservation. capacity is the accessible logical prefix. Live count is the number of entities that remain alive. Before compaction, the row extent can exceed live count because deleted rows still occupy holes.

The stable-address promise

Growth maps additional pages at the same address. Compaction gathers into persistent scratch and copies back into the original columns. Captured graphs and external tensor views keep the same pointers and reserved shapes.

Stable addresses do not make the full reservation readable. Consumers must use valid live ranges, and the table must outlive every graph or tensor that holds its pointers.

2. Entity identity survives row movement

A row index is a location, not an identity. Entity stores a slot plus a 64-bit generation. slot_to_row maps a valid slot to its current row; generation rejects handles to deleted or recycled entities.

APPENDReserve bounded rows. Initialize metadata; the caller writes components.
→
DELETEMark alive 1→0 once; invalidate the slot and increment its generation.
→
COMPACTMove surviving rows, update slot locations, and recycle unused slots.

Deletion decreases live count immediately but does not free an append position. Compaction reclaims the holes. Duplicate deletion returns false without decrementing live count twice. clear() invalidates all surviving handles, resets the extent and world offsets, and reconstructs the free-slot pool while retaining physical memory and sticky errors.

Generation wraparound is possible after 264 reuse cycles. Append, delete, resolve, and compact phases require ordered exclusive stream use; the implementation does not support arbitrary concurrent readers and writers.

3. Compaction creates contiguous world ranges

The table counts live rows for each world, scans those counts into offsets, assigns destination rows, gathers data into scratch, and copies it back. Entity slots are remapped and free slots are rebuilt.

1 / HISTOGRAM + SCANCount live worlds → exclusive offsets.
2 / DESTINATIONSWorld offset + atomic local position.
3 / GATHER + COPY BACKMove components, world IDs, and entity slots.
4 / REMAP + RECYCLERefresh slot→row; recover unused slots.

A world’s range is [world_offsets[w], world_offsets[w + 1]). The sentinel at num_worlds is the end of the live prefix. These ranges are refreshed by compact() and become stale after subsequent appends or deletions. append_worlds() returns separate, temporary offsets for the newly appended batch; it does not refresh the table’s compacted world ranges.

Grouping by world is guaranteed; order within a world is unspecified. Atomic destination assignment does not preserve insertion order or produce a deterministic sort key. Use entity handles for identity and add an explicit sorting stage if a consumer requires deterministic order.

Compaction is not free. It traverses the current extent, copies live component bytes through persistent scratch, processes world counts, and scans committed slots to rebuild the free pool. A sparse table with a large committed capacity can therefore remain expensive even with few live rows.

4. Logical growth and physical growth are separate

Inside a captured graph

Kernels can append, delete, clear, and compact within the committed budget. Fixed launch widths use grid-stride loops over device counts. The graph can replay with different logical populations without changing column addresses or recapturing.

An append uses a bounded atomic reservation. An invalid world, negative batch size, or exhausted capacity sets a sticky error. Single/bulk row reservation returns −1 on failure; append_worlds() fails its entire batch and returns −1 offsets. Components must only be written after successful reservation.

Between completed replays

The host calls ensure_capacity(rows). It synchronizes the device, commits every column and scratch region, initializes new slots, then publishes the larger logical capacity. Growth is forbidden during graph capture.

Commit does not happen on a GPU demand fault. Failed work is not retried automatically, and growth does not clear errors. The caller checks failures, grows outside capture, clears errors deliberately, and retries the inputs that failed.

HOST / STARTUPReserve max_rows. Commit a known sufficient budget. Warm up kernels.
→
GPU / REPLAYChange live rows within capacity. No host allocation or implicit growth.
→
HOST / OPTIONAL GROWTHFinish replay. Check errors. Map more pages before retrying.

The page minimum matters

Each user column has its own virtual-memory region and its own persistent scratch region. Metadata adds five int32 regions (world, alive, entity, slot→row, free slots), one uint64 generation region, and three int32 scratch regions (world scratch, entity scratch, destinations). With C user columns, that is 2C + 9 independently rounded regions, plus fixed counters and world/batch scan arrays.

On the reported RTX PRO 6000 test device, each nonempty committed region has a 2 MiB minimum mapping granule. A two-column table has 13 regions: at least 26 MiB plus fixed metadata, even for one accessible row. The five-column contact snapshot has 19 regions: at least 38 MiB plus fixed metadata. Query VirtualMemory.granularity on another device; 2 MiB is a measured device property, not a universal constant.

Physical storage is approximately Σ round_up(capacity × item_size, device_granule) + fixed_array_bytes, summed across all independent regions. Persistent scratch roughly doubles user-component storage. Page rounding can dominate small tables; pooling metadata or sharing slabs is a possible future design, not implemented here.

committed_bytes includes table-owned mapped regions and fixed arrays. It excludes utility scan workspace, CUDA context, graphs, compiled kernels, driver state, and allocator caches. Reserved address space is not the same as mapped device memory. The prototype does not uncommit pages or shrink after deletion.

5. A minimal producer and consumer

The caller defines component types and initializes every successfully reserved row. Producers and consumers execute in separate, ordered kernel launches. This illustration uses a single-row producer; known per-world batch counts can use append_worlds(counts) to avoid per-row reservation contention.

import warp as wp
from warp.experimental.table import DynamicTable, TableState, append_row

@wp.kernel
def create(state: TableState, positions: wp.array[wp.vec3]):
    world = wp.tid()
    row = append_row(state, world)
    if row >= 0:
        positions[row] = wp.vec3(float(world), 0.0, 0.0)

@wp.kernel
def consume(offsets: wp.array[int], positions: wp.array[wp.vec3]):
    world = wp.tid()
    for row in range(offsets[world], offsets[world + 1]):
        positions[row] += wp.vec3(0.0, 1.0, 0.0)

worlds = 8192
table = DynamicTable({"position": wp.vec3}, max_rows=worlds * 16,
                     num_worlds=worlds, initial_capacity=worlds, device="cuda:0")

def lifecycle():
    table.clear()  # This example replaces the population; surviving handles are invalidated.
    wp.launch(create, dim=worlds, inputs=[table.state, table.columns["position"]])
    table.compact()
    wp.launch(consume, dim=worlds,
              inputs=[table.world_offsets, table.columns["position"]])

lifecycle()  # Warm up JIT compilation and utility scratch before capture.
with wp.ScopedCapture(device=table.device) as capture:
    lifecycle()
wp.capture_launch(capture.graph)
table.check_errors()  # Synchronizes; perform after replay, outside capture.
Bulk append and handle operations

append_worlds(counts) accepts an int32 array of length num_worlds on the table’s device. It scans counts in int64, reserves the combined extent once, and initializes metadata in parallel. Initialize components in a following kernel using the returned per-world batch offsets. Those offsets are overwritten by the next bulk call.

Inside kernels, entity_at(state, row) obtains a handle from a valid live row; find_row(state, handle) returns its current row or −1; delete_entity(state, handle) deletes it once. Keep handles rather than row numbers across compaction. live_count and check_errors() read back device counters and synchronize.

Do not call numpy(), zero_(), or fill_() on a full reserved column if its suffix is unmapped. Use a view bounded by the committed/live range. All launches above must target the selected table device and the same ordered stream.

6. Earlier integration: downstream snapshot

MuJoCo Warp already stores native contacts in globally packed buffers per model batch. This earlier integration uses DynamicTable as a downstream snapshot. The direct native arena described below removes that duplication for sequential model batches.

NATIVE PHYSICSCollision detection, constraints, and integration use existing native buffers.
→
SNAPSHOTClear old rows. Count contacts per world, reserve one batch, then scatter components.
→
WORLD GROUPINGCompact into contiguous logical-world ranges.
→
GPU CONSUMERInspect, record, or export component columns and world offsets.

ContactTable.rebuild(groups) runs after native physics. Each model group supplies a device map from physical world slots to logical world IDs; −1 skips inactive slots. Rebuild histograms native contacts per logical world, calls append_worlds() once, and scatters components into each world’s reserved range before compaction. This avoids every contact contending on the same global append counter. The generic append() path still supports per-contact append but can incur heavy contention at large populations. The copy records position, the first row of the native contact frame as normal, signed depth −contact.dist, and local geometry IDs. Normals point from geom1 to geom2; margin contacts can have negative depth. Geometry IDs remain local to the source model.

The adapter clears the prior snapshot each rebuild, so contact entities do not retain stable identities across simulation steps. General DynamicTable handles survive compaction within a population; this particular snapshot lifecycle intentionally replaces that population. Native or table overflow is sticky and must be checked after replay. A partially copied snapshot is not a complete contact set.

The demonstration keeps 1, 4, or 12 spheres in each world and resets drops every 128 steps. Objects and model assignments stay fixed; contact rows appear and disappear. Startup commits the snapshot budget, warm-up compiles kernels, and each captured replay steps physics, rebuilds the snapshot, and records samples entirely on the GPU. Readback happens after the rollout.

Reducing nconmax/naconmax reduces native capacity and can reduce native array storage. The table itself adds memory and copying; it does not cause that saving or replace solver storage. The demo compares three allocations to keep that distinction visible.

Small-table overhead

The 2 MiB per-region mapping minimum makes this layout unattractive for tiny snapshots: a nine-world run uses roughly 40 MiB for the table while native physics arrays are only about 0.3 MiB. Shared slots and stable pointers are useful capabilities, but they do not guarantee a memory win. The measured adapter workspace at 8,192 worlds is 65,540 bytes in addition to 48,496,700 bytes of table-owned mapped storage and fixed metadata.

Separate table-maintenance measurement

The DynamicTable design note reports a separate pure-Warp ECS experiment on RTX PRO 6000: 50 replays averaged 0.078 ms for 57,344 rows and 0.132 ms for 114,695 rows, using 22.3 MiB of table-owned mapped memory and fixed scratch. These figures include clear, batch append, component initialization, and world grouping. They exclude physical growth and MuJoCo physics and must not be compared directly with the contact rollout above.

Repeated performance measurements

Does the table make execution faster?

Seven independently constructed rollouts per variant, alternating execution order, on the same RTX PRO 6000 GPU at 8,192 worlds. CUDA events measure captured GPU rollouts; compilation, allocation, and final host readback are outside the timed interval. Physics state parity is checked in every trial. The pure-Warp example is 1.55× faster (35.7% less rollout time). Its packed buffers process a much smaller capacity and clear less solver-accumulation memory. Those savings outweigh deletion, compaction, and contact table construction for this workload.

The fixed-buffer version owns 704.22 MiB of layout arrays versus 77.13 MiB for the packed version, excluding the same 11.00 MiB of recording buffers. The fixed layout reserves 512 objects and 2,048 contacts in every world. The packed layout commits a tested global envelope of 97,792 objects and 262,144 contacts. These are different capacity guarantees: the packed version cannot support every world simultaneously reaching the fixed per-world maximum. It is a workload-specific capacity-pooling comparison, not evidence that virtual-memory allocation itself executes faster or that tables outperform an optimized standard-allocation packed buffer.

The current mjwarp contact snapshot is 14.8% slower than tight native physics. The table-only measurement establishes that the extra copy, histogram, reservation, and compaction cost remains even without recording. Native mjwarp already packs its solver contacts, so adding a second packed representation does not remove native solver work.

Native contact-capacity tuning gives a small timing reduction and a substantial memory reduction in this scene; that is independent of DynamicTable. A compelling future mjwarp speedup would require the table to replace existing contact storage or enable consumers to skip padded work, rather than retaining both representations. Any integration must measure the complete collision-to-solver path and preserve overflow semantics. We have not demonstrated that speedup yet.

Stable pointers and graph reuse enable flexibility but are not an automatic throughput win over a preallocated fixed buffer, which can also be graph-compatible. Compaction costs scale with extent, components, world counts, and committed slots. Benefits depend on sparsity, burst distribution, component size, and how often compaction is needed.

Current integration / direct native storage

8. One owner for native contacts

NativeContactTable removes the downstream snapshot from the physics path. Native collision appends into the shared columns, and the native solver consumes those exact columns. Independent model batches reuse their storage sequentially.

This specializes the stable-address storage primitive behind DynamicTable: CUDA virtual memory. It deliberately does not use generic ECS entity slots, generations, deletion, or compaction. Native solver contact indices must remain intact. There is no contact-to-table copy, separate contact snapshot, or component gather/copy-back scratch.

COLLISIONNative nacon counter appends contacts.
→
SHARED COLUMNSOne owner; per-model prefix views.
→
NATIVE SOLVERSame contact indices and buffers.
→
AFTER_GROUPConsume current contacts now.
→
REUSENext group overwrites the arena.

Allocate once during Data construction

The owner computes a single native Contact layout, aligning each column start to 256 bytes. One arena backs all columns. Virtual mode reserves and commits that arena with Warp VirtualMemory; default mode uses an ordinary Warp allocation with the same layout.

make_data(contact_storage=owner) constructs native Contact views directly from the owner. It skips allocating independent native contact arrays, so this is replacement storage rather than allocating twice and rebinding later. Per-model views use their existing capacity prefix and pyramid width; efc_address keeps the owner’s row stride.

Same budgets, a shorter lifetime

The independent baseline reserves the sum of per-group capacities. The shared arena needs their maximum because each group completes its full step before the next group begins. Per-group naconmax budgets remain unchanged; this saving does not rely on tighter collision limits.

All users run on one ordered device stream. The complete physics step and its after_group consumer finish before reuse. Capacity is fixed and committed at startup: kernels do not allocate, grow physical pages, or shrink storage inside capture.

Shared contact views are transient. Read them in after_group; earlier groups’ views are stale once another group steps. Do not interleave step1/step2 across groups, reset Data against stale contacts, or retain all groups’ contact arrays as persistent input. Sleeping’s collision passes stay within one complete step. Disable-collision persistent input is unsupported; flex storage must be explicitly enabled.

9. What the prototype does and does not cover

Implemented and checked

  • Bounded appends, atomic batch reservation, and sticky capacity/argument errors.
  • Deletion once, surviving handles across world grouping, and generation invalidation after recycling or clear.
  • Scalar/vector component preservation through gather/copy-back.
  • Stable exported pointers across compaction and host physical growth.
  • Captured replay with device counts, changing populations, and explicit committed-prefix bounds.

Current limits

  • Exclusive ordered stream use; no overlapping mutations across streams or arbitrary concurrent queries.
  • No automatic device demand growth, physical shrinking, autodiff, archetype migration, or deterministic within-world sorting.
  • Per-region page minimum and persistent scratch can outweigh saved row capacity.
  • Compaction scans extent and committed slots; it is not proportional only to live entities.
  • Contact snapshots add storage and do not generalize the native MuJoCo solver’s model layout.

Useful next steps are slab sharing for small metadata, compacting only dirty tables, and an explicit GPU sorting path when order matters. These are engineering directions rather than claims about the current implementation.
