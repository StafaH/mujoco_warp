01 / Foundations

A world is more than its robot.

Imagine a humanoid standing on a floor. Its model is the blueprint: bodies, joints, masses, collision shapes, and actuators. Its state is what is happening now: joint positions, velocities, actuator state, and simulation time.

Advancing the simulation also needs working memory. Collision detection creates contact information. A constraint solver calculates forces that enforce joints and prevent objects passing through one another. These calculations use arrays much larger than the small set of values that describes the current episode.

Memory category Examples Lifetime in this design
Model Geometry, masses, joints, actuator definitions One prepared description per catalog model, shared by its worlds
Persistent state qpos positions, qvel velocities, controls, time, history One permanent row per logical world
Physics workspace Contacts, constraints, solver matrices One working batch reused across worlds and models
Temporary scratch Intermediate calculations and scan workspace A prepared buffer reused after each phase finishes

A GPU kernel is a function executed by many GPU threads. Warp compiles kernels written using Python syntax. MuJoCo Warp supplies kernels for physics. A batch lets these kernels process many independent environments together.

In a homogeneous batch, every world uses the same model. The rows of its arrays have the same width and meaning. In a heterogeneous population, a humanoid and an arm need different numbers of joints, different collision work, and different action layouts.

02 / The storage problem

Three ways to fit different robots.

Sleep a combined model

Put the possible robots into a common model and disable unused trees in each world. Sleeping avoids work, but allocations still represent the larger combined model.

Useful for inactive bodies; inactive state still has a memory cost.

Keep separate model batches

Give humanoids one compact batch, arms another, and dual arms another. Each batch runs ordinary specialized physics.

Fast for known capacities. A batch with 2,731 humanoid slots cannot hold 8,192 humanoids.

Pool the working batch

Keep persistent state for every world, then process model-specific chunks through shared physics storage.

Any world can choose any catalog model, including the entire population choosing one model.

The repository contains both HeterogeneousWorlds, with fixed model capacities and GPU resets, and PooledHeterogeneousWorlds, which handles arbitrary population mixtures within the startup catalog. The pooled runner is the focus of this report.

03 / The pooled design

A permanent world ID, a temporary working row.

World 42 keeps its identity across episodes. It can contain a humanoid now and an arm after its next reset. A GPU array, world_model_ids, records its current model. Arrays such as state.qpos[42] and state.qvel[42] hold its persistent state.

While its physics runs, world 42 temporarily occupies a row in the shared workspace. Once the result is saved, that row can serve a different world. Policy and episode code address the stable logical world ID.

Small state, padded for stable rows

Each persistent field uses the largest width needed by any catalog model. A smaller robot uses only the valid prefix. This spends some padding to preserve a simple world-indexed interface. Persistent state was 7.63 MB for all 8,192 tested worlds.

Large workspace, reused over time

Each chunk gathers state, runs existing mjwarp physics, and scatters results. Model-specific Data layouts overlap in one arena. The physical cost follows the largest working layout, rather than a complete population allocation for every model.

The GPU counts worlds by model, calculates the beginning of each model’s range, and places world IDs into a grouped list. Relative order within a model is unspecified. Captured worklists rebuild only when assignments change.

Independent worlds all advance by the same simulation timestep, even though their chunks execute successively. The last partially filled chunk currently simulates unused working rows and discards their results.

04 / Reset and reassignment

Follow a world as it changes robots.

A GPU episode kernel writes a destination model ID into reset_model_ids[world]. A value of -1 means no reset. A request for the current model starts a fresh episode of the same robot.

  1. Decide: episode logic reads the preceding state and produces reset requests.
  2. Validate: GPU kernels check that every requested model exists in the catalog.
  3. Assign: valid requests update model IDs and worklists. Each selected world’s epoch increases, and its request becomes -1.
  4. Initialize: selected worlds receive their new model’s reset defaults. Their old episode state is discarded.
  5. Act: GPU policy kernels write controls using the current model’s action layout.
  6. Simulate: grouped chunks advance physics and save updated state and requested observations.

An epoch is a reset counter. It distinguishes different episodes with the same world ID. Invalid requests reject the entire reset transaction: assignments and epochs stay unchanged, requests remain pending, and physics can continue the existing episodes.

05 / CUDA execution

Fixed graph structure, changing GPU decisions.

A CUDA graph records GPU operations and their dependencies so the CPU can submit the sequence efficiently. During capture, Python builds that sequence. During replay, device values determine whether conditional branches run and how many times conditional loops repeat. NVIDIA documents these graph mechanisms.

Episode logicRead prior state; produce reset requests.
Plan and resetValidate, regroup, and initialize selected worlds.
PolicyWrite controls for the current assignments.
Gather chunkCopy persistent state into working rows.
Advance physicsUse that model’s specialized kernels.
Scatter and repeatSave results; loop over remaining chunks and models.

The CPU prepares the system and submits graph launches. Reset decisions, assignments, and chunk-loop decisions execute on device. No reset readback, host allocation, or recapture is needed during replay.

Why a new scratch API was necessary

Existing physics functions create temporary arrays, including workspace used by native scan routines. CUDA conditional body graphs restrict node types and exclude allocation/free nodes. To capture a full physics step inside a conditional loop, we supply its temporary storage in advance. Conditional-body requirements

wp.ScopedCaptureScratch directs Python and participating native allocations into slices of a prepared buffer while the graph is constructed. The recorded kernels use those fixed addresses at replay. rewind() allows later captured phases to reuse the same addresses; it is a construction-time operation, not a runtime GPU allocation.

Reuse requires ordering

Model branches sharing workspace execute sequentially. Callback temporaries must finish before physics reuses their scratch. Concurrent graph executions cannot safely share the same working and scratch storage.

Reuse requires initialization

Another model can overwrite every byte in an aliased region. Required state is gathered or seeded; other fields are recomputed. Dense constraint padding is cleared before each chunk after tests exposed solver failures from stale padding.

Persistent integration state includes more than positions and velocities: actuator history, delayed sensor state, warm-start information, applied forces, mocap inputs, equality activation, and user data also matter. Correctness depends on preserving each field the next step needs.

06 / Memory fundamentals

An address reservation is not physical memory.

A pointer is an address used to access memory. CUDA virtual memory management separates reserving an address range from providing physical GPU memory behind it. Physical backing can be mapped into a reserved range without moving existing data. NVIDIA’s VMM introduction

The new Warp primitive wp.VirtualMemory reserves addresses, commits physical backing, and exposes typed array views with stable pointers. In this prototype, physical commitment uses a host API and synchronizes before growth completes.

The pooled reset path commits its physical memory at startup. Runtime robot changes alter assignments and reuse existing storage. They do not obtain new pages or call a host mapping service.

Meaning of “dynamic” Current implementation
Change what occupies prepared memory GPU-only world reassignment, resets, worklists, and bounded entity-table mutations
Add more physical backing Supported by the standalone VMM primitive through a host boundary; not used during pooled replay

The pooled implementation currently uses VMM for its arena, but a sufficiently large ordinary allocation could support the same algorithm. Grouping and sharing storage account for the main savings. VMM is valuable when contiguous storage needs stable-address growth; it does not automatically make physics faster.

07 / The Madrona connection

Dynamic tables are a separate foundation.

An entity-component system (ECS) stores objects through component tables. Position, velocity, and mass can be separate contiguous columns. Grouping related entities helps GPU access patterns. Madrona uses virtual memory to grow contiguous component storage while preserving addresses used for tensor export. Madrona paper, section 5

In the checked-out Madrona implementation, device code sends growth requests to a host allocator thread, which performs the CUDA mapping and signals completion. Our strict GPU-only reset path uses precommitted storage and does not reproduce that host service. See device requests and the host mapping implementation.

The separate Warp DynamicTable prototype supports device-side append, deletion, and grouping within committed capacity. Components remain at stable column addresses. Entity handles contain a slot and generation number, so a deleted entity’s handle becomes invalid when that slot is reused.

What compaction does

Deleted rows leave holes. Compaction gathers live rows together, groups them by world, and updates each surviving handle’s row mapping. Scratch holds intermediate copies, then results return to the original component arrays. The array addresses stay fixed even though entity rows move. Ordering within a world is unspecified.

The pooled mjwarp runner uses dedicated persistent arrays and model worklists. It does not store the entire physics solver in DynamicTable, and it is not a complete ECS rewrite. Physical table growth remains a separate host operation between completed replays.

What zero-copy tensor access means here

Stable persistent GPU arrays can be shared with learning frameworks through tensor interoperability such as DLPack. That avoids copying their contents into a separate framework allocation. Internal gather/scatter still copies data on the GPU. Policy code must use the model ID to interpret valid observation and action widths. DLPack ownership was tested; PyTorch integration itself was not exercised in this environment.

Measurement conditions and accounting

Hardware: NVIDIA RTX PRO 6000 Blackwell Workstation Edition. Software: MuJoCo 3.12.1 and local Warp 1.19.0.dev0. Each working world has capacity for 16 contacts and 64 constraint rows. Timestep: 0.002 s; Newton solver with 10 iterations and 50 line-search iterations. Constant controls are 0.05. A graph launch contains ten timesteps. GPU episode resets occur every 200 steps. Each population stage has five untimed warmup rollouts and five timed 200-step rollouts; reported times are medians measured with CUDA events. No concurrent compute tests ran during the measurements.

Totals include model arrays, persistent state, mappings, reset defaults, committed shared Data, and the entire preallocated scratch budget. CUDA context, compiled code, graph metadata, and allocator caches are excluded. Models and memory are created before timing. The test does not measure rendering, learned policies, or a complete training workload.

How this compares with the earlier paths

The earlier fixed-population comparison measured a sleep union at 627.1 MB and 5.103 million steps/s, and ordinary model groups at 202.4 MB and 6.746 million steps/s, using the tighter tested contact limits. Those memory totals exclude graph scratch, so they must not be treated as directly comparable totals to the pooled figures above.

In a separate GPU-reset benchmark, fixed model batches achieved 7.108 million steps/s for the baseline with periodic resets, 6.940 with reassignment machinery enabled but no type changes, and 6.662 while changing 96 worlds every ten steps. Fixed capacities remain a useful fast path when the population envelope is known.

For fixed homogeneous worlds, the ordinary grouping wrapper was within 0.3% of original mjwarp throughput in the measured runs. The pooled path adds gather/scatter, initialization, and chunk scheduling. Original homogeneous mjwarp reached 11.872 million steps/s for humanoids and 17.984 million for single arms in earlier tests with different reset/warmup conditions. The pooled results establish flexible GPU-driven population changes; they do not establish a homogeneous speedup. Full comparison details are in the engineering report.

09 / Scope and validation

Flexible assignments within a prepared catalog.

Supported in the pooled prototype

  • GPU-produced model requests and same-model resets.
  • Any population distribution across catalog models.
  • Stable logical IDs and persistent state addresses.
  • Device validation, grouping, and chunk scheduling.
  • One unchanged graph across population changes.
  • Selected world-indexed persistent observations.

Prepared or restricted at startup

  • World count, model catalog, and reset defaults.
  • Contact, constraint, workspace, and scratch capacities.
  • All physical backing needed for replay.
  • No insertion of new bodies/joints into a running model.
  • Pooled sleeping is unsupported; derived caches need extra persistence.
  • Global policy kernels replace model control callbacks.

A memory budget does not guarantee enough contact or constraint capacity for every task. Configure those capacities for the scene. The pooled runner records sticky per-world overflow and nonfinite-state diagnostics, so later workspace reuse or episode resets do not hide earlier failures.

Correctness checks compare pooled simulation against independent physics runs. They cover all four integrators, contacts on translated and rotated static planes, delayed actuators and sensors, mocap and user data, applied forces, invalid transactions, multiple chunks, and unchanged state pointers. Focused GPU-loop tests make host array readback and explicit device synchronization functions fail if called during capture/replay.

Validation result: 383 passed, 11 skipped across the experimental suite and existing IO, forward, sleeping, and history regressions. Final lint and kernel checks passed. Warp tests additionally cover capture scratch, virtual-memory ownership/growth, dynamic tables, and allocator/graph regressions. These checks establish prototype behavior for the covered cases; they are not a claim of production completeness.

Next engineering steps include avoiding vacant-row physics, reducing temporary scratch through finer lifetime reuse, packing persistent fields where padding becomes expensive, preserving sleeping caches, and building richer model-specific action and observation interfaces.
